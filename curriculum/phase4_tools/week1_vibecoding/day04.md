# Day 64: API와 마이크로서비스 — 모델을 서비스로

> 이전 학습에서 바이브코딩으로 분자 물성 예측 웹앱(Day 63)을 하나의 완결된 화면으로 만들었습니다. 오늘은 그 안에 있던 "구조를 넣으면 판단이 나오는" 예측 로직을 화면에서 떼어내, **여러 제품이 함께 호출할 수 있는 독립 서비스(API)**로 만드는 법을 학습합니다. 웹앱이 "하나의 완제품"이라면, API는 "여러 완제품이 공유하는 부품 공장"입니다.

## 개요

**API(Application Programming Interface)**는 프로그램이 다른 프로그램의 기능을 호출하는 약속된 창구이며, **마이크로서비스(microservice)**는 하나의 기능(예: 물성 예측)만 독립적으로 실행·배포되는 작은 서비스 단위입니다. Day 63의 Streamlit 앱은 화면·계산·예측이 한 덩어리로 붙어 있었습니다. 이 구조는 데모에는 좋지만, 같은 예측 로직을 모바일 앱·배치 스크리닝·파트너사 시스템이 동시에 쓰려는 순간 한계에 부딪힙니다. 예측 로직을 API로 분리하면, **한 번 만든 모델을 여러 제품·여러 고객이 재사용**할 수 있게 되어 창업자의 자본 효율이 극적으로 올라갑니다. 이것이 SaaS 비즈니스 모델의 기술적 토대입니다.

## 핵심 개념

API의 본질은 **입력·출력 계약(contract)**입니다. 호출자는 내부 구현을 몰라도, "이 주소에 SMILES를 이 형식으로 보내면, 물성을 이 형식으로 돌려준다"는 약속만 알면 됩니다. 신약개발자에게 익숙한 비유를 넘어선 실제 대응이 여기 있습니다 — 이는 **분석 시험법(assay)의 표준 프로토콜**과 구조적으로 동일합니다. CRO에 검체를 규정된 형식으로 보내면 규정된 형식의 결과지를 받듯, API는 코드 세계의 표준화된 위탁 창구입니다.

- **REST API**: 웹 표준(HTTP) 위에서 동작하는 가장 흔한 방식. `POST /predict`에 JSON을 보내면 JSON으로 답합니다. 실시간 단건 조회에 적합합니다.
- **동기(synchronous) vs 비동기(asynchronous)**: 단일 분자 예측처럼 빠른 작업은 요청 즉시 답하는 동기 방식으로, 10만 개 화합물 배치 스크리닝처럼 오래 걸리는 작업은 "작업 접수 → 나중에 결과 조회"의 비동기 방식으로 처리합니다.
- **상태 없음(stateless)**: 각 요청은 독립적이어야 합니다. 이 원칙 덕분에 요청이 몰리면 같은 서비스를 여러 개 복제해 부하를 나눌 수 있습니다(수평 확장).

> **모델 서빙(model serving)**은 학습된 모델 파일을 메모리에 올려두고 요청마다 추론(inference)만 수행하는 것입니다. 학습(training)과 서빙은 완전히 다른 작업이며, MVP 단계에서 창업자가 신경 쓸 것은 서빙입니다 — "어떻게 학습시키나"가 아니라 "학습된 모델을 어떻게 안정적으로 응답하게 하나".

## 작동 원리와 아키텍처

Day 63 앱을 API로 분해하면, 화면(프론트엔드)과 예측(백엔드 API)이 네트워크로 분리됩니다. 흐름은 **요청 → 검증 → 추론 → 응답**이며, 각 단계가 명확한 책임을 가집니다.

```
분자 물성 예측 마이크로서비스 구성

1. 엔드포인트 정의:  POST /predict     (단건, 동기)
                    POST /batch       (다건, 비동기 → job_id 반환)
                    GET  /health      (서비스 생존 확인)
2. 요청 검증:  입력 스키마 강제 (SMILES 필드 필수, 타입 체크)
              RDKit 파싱 실패 → HTTP 400 + 명확한 오류 메시지
3. 추론 실행:  기동 시 모델 1회 로드 → 요청마다 추론만 (재로드 금지)
4. 응답 구성:  {값, 단위, "예측/계산" 구분, 불확실성, 모델 버전}
5. 계약 문서:  자동 생성 API 문서(스키마)로 호출자에게 사용법 제공
```

기술 스택은 "바이브코딩으로 빠르게, 그러나 확장 가능하게"를 기준으로 고릅니다.

| 설계 결정 | 선택지 | 초기 창업자 추천 | 이유 |
|-----------|--------|-----------------|------|
| API 프레임워크 | Flask / FastAPI / Django | **FastAPI** | 입출력 스키마 자동 검증·문서화, 비동기 지원 |
| 입출력 검증 | 수동 / Pydantic 스키마 | **Pydantic** | 잘못된 입력을 코드가 아닌 계약으로 차단 |
| 패키징 | 로컬 실행 / Docker 컨테이너 | **Docker** | "내 PC에선 됐는데" 문제 제거, 어디서나 동일 실행 |
| 배포 | 자체 서버 / HF Inference / 클라우드 런타임 | **HF Inference Endpoints** | 모델 서빙 인프라를 직접 안 짜도 됨 |
| 응답 형식 | 값만 / 값+메타데이터 | **값+메타데이터** | 모델 버전·불확실성 없는 예측값은 신뢰 불가 |

바이브코딩 관점의 핵심은, Day 62의 프롬프트 원칙을 API 설계에 그대로 적용하는 것입니다. AI에게 "FastAPI로 `/predict` 엔드포인트를 만들되, 입력은 Pydantic 스키마로 SMILES를 검증하고, 응답에는 값·단위·계산/예측 구분·모델 버전을 포함하라"처럼 **계약을 명세로 넘기면**, AI가 검증·문서화·오류 처리를 갖춘 서비스 골격을 생성합니다. 창업자의 일은 이 계약이 도메인적으로 옳은지 — 단위가 맞는지, 예측값에 불확실성이 붙었는지, 오류 응답이 사용자에게 이해되는지 — 를 검증하는 것입니다.

한 가지 반드시 챙길 설계 결정은 **모델 로딩 위치**입니다. 초보 코드는 요청마다 모델 파일을 디스크에서 다시 읽어 수 초씩 지연을 냅니다. 모델은 서비스 기동 시 한 번만 메모리에 올리고, 요청은 추론만 하도록 지시해야 합니다 — 이 한 줄의 차이가 응답 시간을 수 초에서 수십 밀리초로 줄입니다.

## 신약개발 적용

"모델을 API로 제공"하는 형태는 이미 신약개발 인프라의 표준입니다. **AlphaFold**의 구조 예측은 EBI가 제공하는 데이터베이스·API를 통해 전 세계 연구자가 자기 파이프라인에 끌어다 쓰고, 화학 데이터베이스 **ChEMBL**과 **PubChem**은 REST API로 화합물·활성 데이터를 프로그램적으로 조회하게 합니다. 즉 현대 신약개발 워크플로는 "여러 예측·데이터 마이크로서비스를 조합하는 것"으로 이뤄집니다.

산업 사례로, 클라우드 사업자들은 신약개발 특화 모델을 API로 판매합니다. 예컨대 AWS·엔비디아 등이 제공하는 생성·예측 모델을 API 호출로 쓰면, 바이오텍은 GPU 인프라나 모델 학습 없이 추론 결과만 소비할 수 있습니다. 창업자에게 이것은 양날의 검입니다 — 남의 API를 조합해 빠르게 제품을 만들 수 있지만, 핵심 예측이 남의 API에만 의존하면 해자가 없습니다. **어떤 예측을 직접 서빙(내 데이터·내 모델)하고 어떤 것을 외부 API로 조달할지**를 가르는 판단이 곧 기술 전략이 됩니다.

## 창업 관점

API화는 단순한 기술 선택이 아니라 **비즈니스 모델의 전환점**입니다. Day 63의 웹앱은 "한 사용자가 화면에서 쓰는 도구"였지만, API는 "여러 고객·여러 시스템이 사용량만큼 지불하는 제품"이 됩니다. 여기서 세 가지 창업적 기회가 열립니다.

- **과금 모델의 다양화**: API는 호출 건수·배치 규모로 자연스럽게 계량됩니다. 월 구독(seat 기반) 대신 **사용량 기반 과금(usage-based)**이 가능해져, 소규모 바이오텍은 소액으로 시작하고 대형 고객은 규모에 비례해 지불하는 구조를 만들 수 있습니다.
- **파트너 통합(B2B2X)**: 예측 API를 다른 회사의 ELN(전자연구노트)·스크리닝 플랫폼에 끼워 넣으면, 내 화면 없이도 남의 제품 안에서 매출이 발생합니다. 화면 없는 부품 판매가 오히려 시장을 넓힙니다.
- **모듈형 확장**: 물성·독성·용해도 예측을 각각 독립 마이크로서비스로 분리하면, 하나를 고쳐도 나머지가 멈추지 않고, 잘 팔리는 모듈에만 자원을 집중할 수 있습니다.

시장 관점에서 예측·데이터 API 시장의 초기 고객은 Day 63과 같은 **소규모 바이오텍·CRO·학계**지만, API는 여기에 더해 **다른 소프트웨어 회사(플랫폼 벤더)**라는 두 번째 고객군을 엽니다. MVP 전략은 "Day 63 앱의 예측 로직을 `/predict` 하나로 떼어내 문서화된 API로 공개 → 초기 사용자에게 API 키를 발급해 실제 호출 패턴(어떤 물성을 얼마나 자주 부르는가)을 관측 → 가장 많이 불리는 예측을 특화·고도화"입니다. 약학 지식의 우위는 여기서도 유지됩니다 — API 응답에 어떤 임상적 메타데이터(임계값 초과 플래그, 규제 관점 경고)를 담을지는 도메인 전문가만 설계할 수 있고, 이것이 범용 예측 API와의 차별점이 됩니다.

## 오늘의 과제

1. **API 계약 설계 (50분)**: Day 63에서 설계한 앱의 예측 기능을 `/predict` 엔드포인트로 분리한다고 가정하고, (a) 요청 JSON 스키마(필드·타입), (b) 응답 JSON 스키마(값·단위·계산/예측 구분·불확실성·모델 버전), (c) 발생 가능한 오류와 각 HTTP 상태 코드(예: 잘못된 SMILES → 400)를 1페이지 계약 문서로 작성하세요. 이것이 AI에게 넘길 명세입니다.

2. **공개 API 해부 (40분)**: ChEMBL 또는 PubChem의 REST API 문서를 열어 화합물 조회 엔드포인트 하나를 골라, (a) 어떤 입력을 받고, (b) 응답에 어떤 필드가 있으며, (c) 내가 만들 예측 API가 이 데이터를 어떻게 입력으로 조합할 수 있을지를 표로 정리하세요.

3. **make vs buy 판단 (40분)**: 본인의 관심 제품에 필요한 예측·데이터 기능 4가지를 나열하고, 각각을 "직접 서빙(내 해자)" 또는 "외부 API 조달(속도 우선)"로 분류한 뒤 그 이유를 한 줄씩 쓰세요. 특히 어떤 예측을 직접 소유해야 경쟁 우위가 생기는지 도메인 근거와 함께 판단하세요.

- **AlphaFold Protein Structure Database (EBI/DeepMind)**: 구조 예측 결과를 API·데이터베이스로 개방한 사례 — "모델을 서비스로" 개방이 어떻게 연구 생태계를 바꾸는지 보여주는 기준점.
