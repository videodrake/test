# Day 68: MLOps — 실험 추적, 모델 관리, 재현성

> 어제(Day 67)는 RDKit·PyG·HuggingFace·Ollama로 이어지는 오픈소스 스택을 다뤘습니다. 도구를 조합해 모델을 만들 수 있게 되면, 곧바로 새로운 문제에 부딪힙니다 — "어제 성능이 좋았던 그 모델을 어떻게 다시 만들지?" 오늘은 이 질문에 답하는 **MLOps(Machine Learning Operations)**, 그중에서도 실험 추적·모델 관리·재현성을 학습합니다. 이 세 가지는 스타트업이 실험 단계에서 규제 대응 제품으로 넘어가는 다리입니다.

## 개요

MLOps는 머신러닝 모델을 **실험에서 운영까지 체계적으로 관리하는 방법론과 도구**입니다. 오늘 다루는 세 축은 (1) 어떤 설정으로 무슨 결과가 나왔는지 기록하는 **실험 추적(experiment tracking)**, (2) 학습된 모델의 버전을 관리하는 **모델 레지스트리(model registry)**, (3) 같은 입력으로 같은 결과를 다시 얻는 **재현성(reproducibility)**입니다. 신약개발에서 이 세 가지는 단순한 편의 기능이 아니라 규제의 최전선입니다. FDA·MFDS가 AI 모델을 의사결정에 활용하려면 "그 예측이 어떻게 나왔는지 추적·재현 가능해야 한다"고 요구하기 때문입니다. 약학 전공자가 데이터 무결성(data integrity)과 검증(validation)의 규제 의미를 이미 안다는 점에서, MLOps는 도메인 강점이 기술 설계로 직결되는 대표적 영역입니다.

## 핵심 개념

세 축의 정의와 역할을 구분합니다.

- **실험 추적(experiment tracking)**: 모델을 학습할 때마다 사용한 **하이퍼파라미터, 데이터셋 버전, 코드 버전, 평가 지표, 산출물(모델 가중치·그래프)**을 자동으로 기록하는 것입니다. 대표 도구는 **MLflow**(오픈소스)와 **Weights & Biases(W&B)**(상용+무료 티어)입니다. 수십·수백 번의 실험을 손으로 스프레드시트에 적는 대신, 코드 몇 줄로 모든 실행을 데이터베이스에 남깁니다.
- **모델 레지스트리(model registry)**: 학습이 끝난 모델에 **버전 번호와 단계(Staging/Production/Archived)**를 붙여 관리하는 저장소입니다. "지금 서비스에 배포된 모델은 v3이고, v4는 검증 중"이라는 상태를 명시적으로 관리합니다. 어떤 데이터·코드로 만든 모델인지 추적(lineage)이 함께 기록됩니다.
- **재현성(reproducibility)**: 동일한 코드·데이터·환경으로 실행하면 **동일한(또는 통계적으로 동등한) 결과**가 나오도록 보장하는 것입니다. 이를 위해서는 난수 시드(random seed) 고정, 라이브러리 버전 고정(예: `requirements.txt`, 컨테이너), 그리고 **데이터 버전 관리(data versioning)**가 필요합니다. 데이터 버전 관리 도구로는 **DVC(Data Version Control)**가 대표적입니다.

> 핵심: 코드는 Git으로 버전 관리하지만, **데이터와 모델은 Git에 담기 어렵습니다**(용량이 크고 바이너리이기 때문). MLOps 도구는 "코드 = Git, 데이터 = DVC, 모델·실험 = MLflow/W&B"처럼 각 자산에 맞는 버전 관리 계층을 제공합니다.

약학 전공자의 관점에서 재현성은 낯선 개념이 아닙니다. **GLP(우수실험실기준)·GMP(우수제조기준)**에서 실험과 제조 기록을 남기고 재현 가능하게 하는 것, 그리고 **데이터 무결성 원칙 ALCOA+**(Attributable·Legible·Contemporaneous·Original·Accurate에 Complete·Consistent·Enduring·Available를 더한 규제 표준)는 MLOps의 실험 추적과 정확히 같은 목표를 다른 언어로 말한 것입니다. 이 대응을 아는 사람이, "왜 이 로그를 남겨야 하는가"를 규제 심사관에게 설명할 수 있습니다.

## 작동 원리와 아키텍처

Phase 4의 목표대로, MLOps 도구가 학습 워크플로에 어떻게 끼어드는지 구조로 이해합니다. 입력(데이터+코드)에서 출력(추적된 모델)까지의 흐름입니다.

```
MLOps 파이프라인:
1. 데이터 버전 관리(DVC): 원본 데이터셋 → 해시로 스냅샷 → "data v2.1" 태그
2. 실험 실행 + 추적(MLflow):
   - 입력: 하이퍼파라미터(learning rate, GNN layer 수), data v2.1, git commit hash
   - 처리: 모델 학습 → 매 epoch 지표(loss, AUC) 자동 기록
   - 출력: run_id에 묶인 {파라미터, 지표, 모델 가중치, 환경 정보}
3. 모델 레지스트리: 최고 성능 run → "hERG-predictor v4" 등록 → Staging 단계
4. 검증 통과 → Production 승격 (누가·언제·왜 승격했는지 기록)
```

핵심 설계 결정을 표로 정리합니다.

| 설계 결정 | 선택지 | 추천 상황 | 이유 |
|-----------|--------|----------|------|
| 실험 추적 | MLflow / W&B | 자체 호스팅·데이터 통제 시 MLflow | 오픈소스, 로컬 서버 구축 가능 |
| 실험 추적 | MLflow / W&B | 협업·시각화 우선 시 W&B | UI·팀 대시보드가 성숙 |
| 데이터 버전 | DVC / 수동 폴더 | 재현성·규제 필요 시 DVC | 데이터 해시로 정확한 스냅샷 |
| 환경 고정 | requirements.txt / Docker | 규제·배포 시 Docker | OS·라이브러리까지 완전 고정 |

재현성을 보장하는 세 계층을 분리해 이해하는 것이 중요합니다.

1. **코드 재현성**: git commit hash로 정확한 코드 상태를 지정. 실험 로그에 hash를 함께 기록합니다.
2. **데이터 재현성**: DVC가 데이터셋 내용을 해시(예: SHA-256)로 식별. "data v2.1"이 정확히 어떤 파일이었는지 보장합니다. Day 66에서 다룬 데이터 정제 파이프라인의 각 단계 산출물도 이렇게 버전을 매길 수 있습니다.
3. **환경 재현성**: 난수 시드 고정 + 라이브러리 버전 고정 + (엄격하게는) 컨테이너로 OS·CUDA 버전까지 동결. GPU 연산은 완전한 비트 단위 재현이 어려운 경우가 있어(비결정적 연산), "통계적으로 동등한 재현"을 목표로 하는 것이 실무적입니다.

> 바이브코딩 관점: AI에게 "MLflow로 이 학습 스크립트를 감싸서 파라미터와 AUC를 자동 기록하게 해줘"라고 지시하려면, 무엇이 기록되어야 하는지(파라미터·데이터 버전·지표·산출물)를 아는 것이 먼저입니다. 도구 사용법보다 "무엇을 남겨야 재현·규제 대응이 가능한가"라는 설계 감각이 핵심입니다.

## 신약개발 적용

MLOps가 신약개발에서 특별히 중요한 이유는 **규제와 신뢰성** 때문입니다.

- **규제 재현성 요구**: FDA는 AI/ML 기반 의료·신약 도구에 대해 모델 개발 과정의 투명성과 추적성을 강조해 왔습니다. 특히 학습 데이터, 모델 버전, 성능 평가가 문서화·추적 가능해야 한다는 방향의 가이던스를 제시하고 있습니다(세부 요건은 문서·맥락별로 상이하므로 실제 적용 시 최신 가이던스 확인 필요). 실험 추적·모델 레지스트리는 이 요구를 기술적으로 충족하는 인프라입니다.
- **감사 추적(audit trail)**: 제약 규제의 21 CFR Part 11(전자기록·전자서명)은 "누가·언제·무엇을 바꿨는가"의 감사 추적을 요구합니다. 모델 레지스트리의 버전·승격 기록이 바로 이 감사 추적의 ML 버전입니다. 약학 전공자는 이 규제 언어를 이미 알기에, MLOps 로그를 규제 문서로 번역할 수 있습니다.
- **모델 드리프트(model drift) 감시**: 배포된 모델의 성능은 시간이 지나며 저하될 수 있습니다(새로운 화학 공간의 분자가 들어오면 예측이 부정확해짐). 실험 추적·모니터링 인프라가 있어야 드리프트를 감지하고 재학습 시점을 판단할 수 있습니다. 이는 임상에서 약물의 시판 후 안전성 감시(pharmacovigilance)와 사고 구조가 같습니다 — 배포 후에도 지속 관찰하고 신호가 잡히면 개입합니다.
- **실무 도구의 확산**: MLflow는 오픈소스 실험 추적의 사실상 표준으로 자리 잡았고, 다수 바이오·제약 데이터 과학 팀이 실험 관리에 이를 채택하고 있습니다. DVC는 규제·연구 재현성이 중요한 조직에서 데이터·모델 버전 관리에 활용됩니다.

기존 방식과의 차이는, 과거에는 실험 기록을 연구자 개인의 노트북·스프레드시트에 의존했다면, 이제는 파이프라인에 추적이 내장되어 **재현·감사·규제 대응이 자동화**된다는 점입니다. 이는 수개월 뒤 규제 심사에서 "이 예측의 근거를 재현해 보이라"는 요구를 받았을 때 결정적 차이를 만듭니다.

## 창업 관점

Phase 4답게 MLOps는 스타트업의 신뢰성·비용·해자에 직접 연결됩니다.

- **규제 대응이 곧 제품 가치**: AI 신약개발 스타트업이 제약사에 도구를 팔 때, 제약사가 가장 먼저 묻는 것은 "이 모델을 규제 문서에 넣을 수 있는가"입니다. 실험 추적·재현성·감사 추적을 처음부터 설계에 내장한 제품은, 나중에 규제 요구가 왔을 때 급조하는 경쟁사보다 압도적으로 유리합니다. **약학 전공자는 이 규제 요구를 미리 읽고 제품에 반영할 수 있다는 점이 핵심 차별화**입니다.
- **기술적 해자(moat)의 위치**: Day 67에서 도구가 무료로 평준화되면 해자는 데이터·도메인 지식·운영 노하우로 이동한다고 했습니다. MLOps 인프라는 그 "운영 노하우"를 시스템으로 굳히는 장치입니다. 재현 가능하고 감사 가능한 파이프라인 자체가, 규제 산업에서는 복제하기 어려운 자산이 됩니다.
- **비용 구조**: MLflow·DVC는 오픈소스라 초기 비용이 낮고, W&B는 무료 티어로 시작해 팀 규모에 따라 과금됩니다. 스타트업은 자체 호스팅 MLflow로 시작해 데이터 통제권을 지키면서 비용을 억제하는 전략이 합리적입니다.
- **경쟁 구도**: 범용 MLOps 플랫폼(MLflow, W&B, 클라우드 제공사의 관리형 서비스)이 이미 존재합니다. 스타트업이 이들과 정면 경쟁하는 것은 무모하며, 승부처는 **"신약개발·규제에 특화된 MLOps"** — GxP 준수 템플릿, ALCOA+ 매핑, 규제 문서 자동 생성 같은 도메인 레이어입니다.

> MVP 구상: hERG 예측 모델(Day 67 MVP) 위에, MLflow로 모든 학습 실험을 추적하고 모델 레지스트리로 버전을 관리하는 계층을 얹으세요. 여기에 "각 모델 버전이 어떤 데이터·코드로 만들어졌는지" 요약 리포트를 자동 생성하는 기능을 붙이면, 그 자체가 규제 대응 도구의 최소 형태입니다. "재현 가능하고 감사 가능한 예측"을 판매 포인트로 삼으면, 규제를 두려워하는 제약사에 강력한 메시지가 됩니다.

## 오늘의 과제

1. **(기초 학습)** MLflow가 하나의 실험 실행(run)에서 기록하는 4가지 요소(파라미터, 지표, 산출물, 태그/메타데이터)를 정리하고, 각 요소가 규제의 데이터 무결성 원칙 ALCOA+의 어떤 항목과 연결되는지 대응표를 만드세요. 30분.
2. **(리서치 정리)** "재현성 위기(reproducibility crisis)"를 머신러닝 맥락에서 검색해, ML 연구·실무에서 재현이 어려운 이유 3가지(데이터 미공개, 환경 차이, 난수·비결정성)를 각각 한 문단으로 정리하세요. 신약개발처럼 규제가 재현을 요구하는 산업에서 이것이 왜 더 치명적인지 마지막에 한 문단으로 논하세요. 40분.
3. **(비즈니스 분석)** "규제 특화 MLOps"를 제품으로 판다고 가정하고, 타깃 고객(예: 중소 제약사, CRO, 바이오텍)을 하나 정해 그들이 겪는 재현성·감사 관련 페인 포인트 3가지와 각 페인을 해결하는 기능 가설을 표로 작성하세요. 40분.
