# Day 69: 배포 — Docker, FastAPI, 클라우드 GPU

> 어제(Day 68)는 MLflow·DVC로 모델을 추적·버전 관리하는 MLOps를 다뤘습니다. 레지스트리에 "Production 승격" 도장을 찍은 모델은, 그 순간부터 누군가가 실제로 호출할 수 있어야 가치가 생깁니다. 오늘은 그 마지막 다리 — 학습이 끝난 모델을 **컨테이너(Docker)로 포장하고, API(FastAPI)로 감싸, 클라우드 GPU 위에서 서비스로 돌리는** 배포(deployment)를 학습합니다. 여기까지 와야 "모델"이 "제품"이 됩니다.

## 개요

배포(deployment)는 학습이 끝난 모델을 **다른 사람·시스템이 안정적으로 호출할 수 있는 서비스로 전환하는 과정**입니다. 아무리 성능 좋은 hERG 예측 모델도 여러분의 노트북 주피터 노트북 안에만 있으면 제품이 아닙니다. 오늘 다루는 세 축은 (1) 실행 환경을 통째로 포장하는 **컨테이너화(Docker)**, (2) 모델을 HTTP로 부를 수 있게 감싸는 **API 서버(FastAPI)**, (3) 딥러닝 추론에 필요한 연산 자원을 빌리는 **클라우드 GPU**입니다. 이 셋은 "재현 가능한 환경 → 표준 인터페이스 → 확장 가능한 자원"이라는 배포의 3단 논리를 이룹니다. 약학 전공자에게 이 단계는 규제와 직결됩니다 — 배포된 모델이 곧 의사결정에 쓰이는 순간, 그 버전·환경·응답이 모두 추적 가능해야 하기 때문입니다.

## 핵심 개념

세 도구의 역할을 먼저 구분합니다.

- **Docker(컨테이너)**: 코드·라이브러리·시스템 설정을 하나의 이미지(image)로 묶어, 어떤 컴퓨터에서도 **동일하게 실행**되게 하는 기술입니다. "내 컴퓨터에서는 됐는데요"라는 재현성 문제를 원천 차단합니다. Day 68에서 배운 재현성의 환경(environment) 축을 실제로 강제하는 장치가 바로 컨테이너입니다.
- **FastAPI**: 파이썬으로 **웹 API를 만드는 프레임워크**입니다. 모델의 `predict()` 함수를 `POST /predict` 같은 HTTP 엔드포인트로 노출시켜, 웹앱·다른 서비스·외부 고객이 표준 방식(JSON 요청/응답)으로 모델을 부를 수 있게 합니다. 타입 힌트 기반 자동 문서화(Swagger UI)와 비동기 처리 성능이 강점입니다.
- **클라우드 GPU**: 딥러닝 추론(inference)은 CPU로는 느리거나 불가능한 경우가 많아 **GPU 연산**이 필요합니다. 이를 소유하지 않고 시간 단위로 빌리는 것이 클라우드 GPU입니다. 대표적으로 AWS·GCP·Azure의 GPU 인스턴스, 그리고 **Modal·RunPod·Replicate·Lambda Labs·Hugging Face Inference Endpoints** 같은 배포 특화 서비스가 있습니다.

> 핵심 구분: **학습(training) GPU와 추론(inference) GPU는 요구가 다릅니다.** 학습은 크고 오래(수 시간~수일) 강력한 GPU(예: NVIDIA A100/H100)를 점유하지만, 추론은 짧고(수십 ms~수 초) 자주 호출됩니다. 배포 단계에서 신경 쓸 것은 대개 추론 비용 — "요청 하나당 몇 원이 드는가"입니다.

또 하나의 핵심 개념은 **레이턴시(latency)와 처리량(throughput)의 구분**입니다. 레이턴시는 요청 하나에 걸리는 시간, 처리량은 단위 시간당 처리하는 요청 수입니다. 분자 하나를 예측하는 대화형 도구라면 레이턴시가, 수백만 분자를 스크리닝하는 배치 작업이라면 처리량이 중요합니다. 이 구분은 약학의 **약동학에서 Cmax(최고 농도, 반응 속도)와 AUC(총 노출량, 총 처리량)를 나눠 보는 사고와 구조적으로 같습니다** — 무엇을 최적화할지에 따라 설계가 달라집니다.

## 작동 원리와 아키텍처

Phase 4의 목표대로, 모델 하나가 어떻게 서비스가 되는지 입력→처리→출력 흐름으로 이해합니다. 바이브코딩으로 이 시스템을 만들 때 AI에게 지시할 구조입니다.

```
배포 파이프라인:
1. 모델 로드: MLflow 레지스트리에서 "Production" 태그 모델 v3 내려받기
2. API 래핑(FastAPI):
   - 엔드포인트 POST /predict
   - 입력: {"smiles": "CC(=O)Oc1ccccc1C(=O)O"}
   - 처리: SMILES → 특성화 → model.predict() → pIC50
   - 출력: {"pIC50": 6.8, "model_version": "v3", "uncertainty": 0.4}
3. 컨테이너화(Docker):
   - 베이스 이미지(python:3.11) + requirements.txt + 모델 파일 + API 코드
   - → 하나의 이미지로 빌드
4. 클라우드 GPU 배포:
   - 이미지를 GPU 인스턴스(또는 Modal/RunPod)에 올림
   - 오토스케일링: 요청 없으면 0으로, 몰리면 N개로
```

배포 아키텍처의 핵심 설계 결정을 표로 정리합니다.

| 설계 결정 | 선택지 | 스타트업 초기 추천 | 이유 |
|-----------|--------|------------------|------|
| 서빙 방식 | 상시 가동 서버 / 서버리스(요청 시 기동) | 서버리스 | 트래픽 적은 초기엔 유휴 GPU 비용이 치명적 |
| GPU 조달 | 자체 구매 / 클라우드 상시 / 온디맨드 | 온디맨드·서버리스 | 자본지출 없이 사용량만큼 지불 |
| 추론 최적화 | 원본 모델 / 양자화·배치 | 배치 처리 우선 | 스크리닝은 묶어서 처리해야 단가 하락 |
| 응답 로깅 | 없음 / 전량 기록 | 전량 기록 | 규제·감사·재학습 데이터 확보 |

> 서버리스 GPU(예: Modal, Replicate)의 핵심 가치는 **"scale to zero"** — 요청이 없으면 GPU를 0개로 내려 비용이 나지 않고, 요청이 오면 컨테이너를 기동합니다. 대신 첫 요청 시 컨테이너를 띄우는 지연(cold start)이 생기므로, 대화형 제품에서는 이 지연을 관리하는 설계가 필요합니다.

## 신약개발 적용

배포는 추상적 인프라가 아니라, AI 신약개발의 실제 제품이 사용자에게 닿는 지점입니다.

- **분자 생성·예측 서비스의 API화**: **Chemify·Chai Discovery·Iambic** 등 최근 창업된 AI 신약개발 기업들은 모델을 내부 파이프라인과 파트너 제약사가 호출하는 API로 제공합니다. 모델 자체보다 "안정적으로 호출 가능한 서비스"가 사업의 실체입니다.
- **AlphaFold의 배포 형태 비교**: DeepMind의 AlphaFold2는 코드·가중치를 공개했지만, 실제로 많은 연구자는 EMBL-EBI가 운영하는 **AlphaFold DB**(2억 개 이상 예측 구조 사전 계산·배포)나 **ColabFold**(클라우드에서 브라우저로 실행) 같은 배포 계층을 통해 씁니다. 같은 모델이라도 "어떻게 배포되느냐"가 실제 활용도를 좌우함을 보여주는 대표 사례입니다.
- **비용의 현실**: 단백질 구조 예측이나 대규모 도킹 시뮬레이션을 수백만 분자에 돌리면 GPU 시간이 곧 돈입니다. 예컨대 고성능 GPU 온디맨드 단가는 시간당 수 달러 수준(제공사·시점에 따라 상이, 확인 필요)이며, 배치 최적화·양자화로 추론 단가를 낮추는 것이 곧 마진이 됩니다.

기존 방식(연구자가 각자 로컬에서 스크립트 실행)과 배포된 서비스의 차이를 정리합니다.

| 항목 | 로컬 스크립트 | 배포된 API 서비스 |
|------|--------------|------------------|
| 재현성 | 환경마다 결과 흔들림 | 컨테이너로 고정 |
| 접근성 | 코드·GPU 있어야 사용 | HTTP만 있으면 누구나 |
| 버전 관리 | 수동·불명확 | 응답에 모델 버전 명시 |
| 감사·규제 | 기록 없음 | 요청·응답 전량 로깅 |

## 창업 관점

Phase 4답게, 배포는 스타트업의 원가 구조와 제품 경쟁력에 직결됩니다.

- **제품 형태와 시장**: AI 신약개발 도구의 대표 판매 형태는 **API 또는 웹앱 형태의 SaaS**입니다. 제약사·바이오텍·CRO가 자체 모델을 만들 여력이 없을 때, "호출만 하면 되는" 예측 서비스는 명확한 가치를 팝니다. 관련 시장은 AI 신약개발 소프트웨어·서비스 시장의 일부로, 연 10억 달러대에서 두 자릿수 성장률로 확대되는 것으로 보고됩니다(출처·연도 확인 필요).
- **원가 = GPU 비용**: SaaS 마진의 최대 변수는 추론 GPU 비용입니다. 서버리스·배치·양자화로 요청당 단가를 낮추는 역량이 곧 가격 경쟁력이며, 이는 순수 소프트웨어 SaaS와 다른 AI 제품 특유의 원가 구조입니다. 가격을 요청당 과금(pay-per-prediction)으로 설계하면 원가와 매출을 직접 연동할 수 있습니다.
- **기술적 해자(moat)**: 배포 기술(Docker·FastAPI·클라우드) 자체는 평준화되어 해자가 아닙니다. Day 67~68의 논리를 이어받으면, 해자는 (1) 도메인 특화 모델 품질, (2) **규제 대응형 배포** — 응답 전량 로깅, 모델 버전 추적, 감사 로그 —, (3) 추론 원가 최적화 노하우에 있습니다. 약학 전공자는 이 중 (2)를 제품 요구사항으로 먼저 정의할 수 있다는 점이 차별화입니다.
- **경쟁 구도**: 범용 배포 플랫폼(Modal·Replicate·HF Endpoints, 클라우드 제공사)과 정면 경쟁하지 말고, 그 위에 얹는 **신약개발 특화 계층**(분자 입력 검증, 화학 특성화 내장, 규제 로깅 템플릿)으로 승부하는 것이 합리적입니다.

> MVP 구상: Day 67~68에서 만든 hERG 예측 모델을 FastAPI로 감싸 `POST /predict` 엔드포인트를 만들고, Docker 이미지로 빌드해 Modal이나 Hugging Face Inference Endpoints 같은 서버리스 GPU에 올리세요. 응답에 모델 버전과 불확실성을 함께 반환하고, 모든 요청·응답을 로깅하면 그 자체가 "규제 대응형 예측 API"의 최소 형태가 됩니다. 여기까지 오면 여러분은 처음으로 "남이 호출할 수 있는 제품"을 갖게 됩니다.

## 오늘의 과제

1. **(기초 학습)** Docker 컨테이너와 파이썬 가상환경(venv/conda)의 차이를 3가지(격리 범위, 재현 대상, 배포 이식성) 측면에서 표로 정리하세요. 그리고 "Day 68의 재현성 3요소(코드·데이터·환경) 중 컨테이너가 책임지는 것은 무엇인가"를 한 문단으로 답하세요. 30분.
2. **(리서치 정리)** 서버리스 GPU 서비스 3곳(예: Modal, Replicate, RunPod, Hugging Face Inference Endpoints 중 택 3)의 가격 모델·cold start·지원 GPU를 검색해 비교표를 만드세요. 각 서비스가 "대화형 예측 도구"와 "대규모 배치 스크리닝" 중 어느 쪽에 더 맞는지 근거와 함께 판단하세요. 40분.
3. **(비즈니스 분석)** hERG 예측 API를 요청당 과금(pay-per-prediction) SaaS로 판다고 가정하고, (a) 요청당 예상 GPU 원가 가설, (b) 목표 마진을 반영한 가격, (c) 규제 대응 기능(로깅·버전 추적)을 유료 상위 티어로 분리하는 패키징 안을 한 페이지로 설계하세요. 40분.
