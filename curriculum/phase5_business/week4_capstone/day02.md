# Day 97: 기술 아키텍처 설계 — AI 파이프라인 완성

> Day 96에서 우리는 회사의 비전·미션·핵심 가치라는 최상위 좌표계를 세우고, "규제 번역 SaaS"를 캡스톤의 대상 회사로 정식화했습니다. 오늘은 그 비전을 실현할 **기술 아키텍처**를 설계합니다. Phase 2에서 배운 분자 표현·물성 예측(QSAR, GNN), Phase 2 후반의 ADMET·단백질 구조, Phase 3의 생성 모델·LLM, Phase 4의 데이터 파이프라인·MLOps·배포를 **하나의 end-to-end AI 파이프라인**으로 조립하는 날입니다.

## 개요

기술 아키텍처(technical architecture)는 "우리가 무엇을 만들고, 무엇을 사서 쓰며, 어디에 고유 기술을 투자할 것인가"를 하나의 시스템 설계도로 표현한 것입니다. 창업 맥락에서 아키텍처 설계의 본질은 기술 선택이 아니라 **자원 배분 결정**입니다 — 제한된 시간과 돈을 어느 컴포넌트에 쓸지, 어디서 오픈소스/API에 올라탈지를 가르는 전략 문서입니다. 특히 AI 신약개발처럼 구성요소(분자 인코더, 예측 모델, 데이터 저장소, 서빙 API, 검증 레이어)가 많은 영역에서는, 아키텍처가 곧 **기술적 해자(moat)의 위치를 정의**합니다. 오늘은 전체 파이프라인을 레이어로 분해하고, 각 레이어에서 "만들 것 vs 살 것(build vs buy)"을 판정하며, 약사-창업자가 해자를 어디에 둘지를 설계합니다.

## 핵심 개념

좋은 기술 아키텍처는 세 가지 질문에 답합니다.

- **데이터는 어디서 와서 어디로 흐르는가** — 데이터 흐름(data flow)
- **각 처리 단계는 무엇을 입력받아 무엇을 출력하는가** — 컴포넌트 경계(component boundary)
- **우리의 고유 가치는 어느 단계에 있는가** — 해자의 위치(locus of moat)

여기서 가장 중요한 개념은 **관심사의 분리(separation of concerns)**와 **레이어화(layering)**입니다. 파이프라인을 독립적으로 교체 가능한 레이어로 나누면, 한 레이어의 기술이 낡아도(예: 분자 인코더를 GNN에서 Transformer 기반 foundation model로 교체) 나머지를 건드리지 않고 갈아끼울 수 있습니다. 이는 기술이 빠르게 바뀌는 AI 분야에서 생존에 직결되는 설계 원칙입니다.

약학 전공자에게 이 레이어 사고는 낯설지 않습니다. 신약개발의 **ADME 구획 모델(compartment model)**은 생체를 흡수·분포·대사·배설이라는 독립적이면서 연결된 구획으로 나누고, 각 구획을 속도상수(k)로 연결합니다. 한 구획의 파라미터가 바뀌어도 모델 구조 전체를 다시 세우지 않고 해당 구획만 보정합니다. **소프트웨어 아키텍처의 레이어는 PK 구획 모델과 구조적으로 동형(isomorphic)**입니다 — 각 레이어가 명확한 입출력(구획 간 질량 이동)을 갖고, 내부 구현은 캡슐화(구획 내부 동역학)된다는 점에서 그렇습니다. 이 사고 훈련을 받은 창업자는 "어디를 고유 기술로 깊게 파고, 어디를 블랙박스로 둘지"를 자연스럽게 판단합니다.

> 핵심 원칙: 아키텍처의 목적은 "최신 기술을 다 쓰는 것"이 아니라 **"우리가 깊게 파야 할 단 하나의 레이어를 고르고, 나머지는 과감히 남의 것을 쓰는 것"**이다. 초기 스타트업의 실패는 대개 모든 레이어를 직접 만들려다 자원이 고갈되는 데서 온다.

## 작동 원리와 아키텍처

규제 번역 SaaS의 end-to-end 파이프라인을 레이어로 분해하면 다음과 같습니다. 각 레이어 옆에 Phase 2~4에서 배운 기술을 매핑했습니다.

```
규제 번역 SaaS — 레이어 아키텍처 (입력 → 처리 → 출력):

[L1] 데이터 수집·정규화 레이어  (Phase1 W4, Phase4 W2)
   입력: 고객의 ADMET/독성 예측 결과, 모델 메타데이터, 실험 데이터
   처리: 스키마 정규화, 단위 변환, 출처·버전 기록(provenance)
   출력: 표준화된 증거 레코드

[L2] 분자·물성 표현 레이어  (Phase2 W1~W3)
   입력: SMILES, 예측값, 신뢰구간
   처리: 분자 표현 정규화 + 예측의 불확실성 정량화
   출력: 임상적으로 해석 가능한 물성 프로파일

[L3] 규제 번역 레이어  ← 우리의 해자 (Phase3 W3 LLM + 도메인 지식)
   입력: 물성 프로파일 + 규제 요구사항(FDA/EMA/MFDS 가이드라인)
   처리: LLM + 규제 지식베이스(RAG)로 '규제 언어' 생성, 위험 플래그
   출력: 규제 제출용 초안 + 근거·불확실성 명시

[L4] 검증·감사 레이어  (Phase4 W3 품질, W4 규제)
   처리: 사람(약무/규제 전문가) 검토 체크포인트, 변경 이력 감사추적
   출력: 검토 완료 문서 + 감사 로그

[L5] 서빙·UI 레이어  (Phase4 W1~W2)
   처리: FastAPI 서빙 + 과학자용 웹 UI + 권한/보안
   출력: 고객 대시보드, API
```

각 레이어에서 "만들 것 vs 살 것"을 판정하면 자원 배분이 선명해집니다.

| 레이어 | 만들기 vs 사기 | 근거 |
|--------|---------------|------|
| L1 데이터 정규화 | **사기**(오픈소스 ETL/RDKit) | 범용 문제, 차별화 없음 |
| L2 분자·물성 표현 | **사기**(RDKit, HuggingFace 사전학습 모델) | 성숙한 오픈소스 존재 |
| L3 규제 번역 | **만들기** ← 핵심 투자 | 도메인 지식이 해자, 모방 난이도 최고 |
| L4 검증·감사 | **만들기(얇게)** | 규제 신뢰성의 원천, 단 자체 로직은 최소화 |
| L5 서빙·UI | **사기**(FastAPI, 클라우드) | 바이브코딩으로 빠르게, 차별화는 UX만 |

이 판정의 핵심은 **L3에만 깊이 투자**한다는 결정입니다. L3은 LLM(범용 모델은 API로 조달)에 **규제 지식베이스를 RAG(Retrieval-Augmented Generation, Phase3 W3 Day04)로 결합**하고, 약학·규제 전문가의 판단을 프롬프트·검증 규칙으로 체화한 레이어입니다. 범용 AI 기업은 L1·L2·L5를 더 잘 만들 수 있어도, L3의 규제·임상 도메인 깊이는 쉽게 복제하지 못합니다. 이것이 아키텍처로 표현된 해자입니다.

## 신약개발 적용

실제 AI 신약개발 회사들의 아키텍처도 "모든 것을 직접 만들지 않는다"는 원칙을 따릅니다.

| 회사 | 깊게 투자한(해자) 레이어 | 외부/표준에 의존한 레이어 |
|------|----------------------|------------------------|
| Recursion | 자체 대규모 세포 이미징 데이터 + 표현형 지도 | 클라우드 인프라, 범용 ML 프레임워크 |
| Isomorphic Labs | 구조 예측(AlphaFold 계열) 자산의 신약화 | 표준 화학정보학 툴체인 |
| Schrödinger | 물리 기반 자유에너지 계산 엔진 | UI·클라우드 배포 등 주변 레이어 |

이들의 공통점은 **단 하나의 레이어(데이터·구조예측·물리엔진)에 수년을 집중 투자**하고 나머지는 표준 도구에 올라탔다는 점입니다(각 사의 공개 자료·기술 블로그 기준, 세부는 시점별 상이, 확인 필요). AlphaFold의 등장(2021, Nature)이 Isomorphic의 아키텍처 중심을 "구조 예측 자산"에 두게 만든 것처럼, 아키텍처는 **"지금 어떤 기술이 성숙했는가"에 따라 해자의 위치를 다시 잡는** 살아있는 결정입니다.

약사-창업자의 결정적 우위는 **L3·L4(규제 번역·검증) 레이어의 품질 기준을 임상적으로 설정**할 수 있다는 점입니다. 비전문 개발자는 "LLM이 그럴듯한 문장을 생성하면 성공"으로 보지만, 약학 훈련을 받은 창업자는 "이 예측의 신뢰구간이 규제 판단을 바꿀 만큼 넓은가", "이 독성 플래그가 hERG 수준의 규제적 중대성을 갖는가"를 판정할 수 있습니다(Phase2 W3 ADMET, Phase4 W4 규제). 즉, 약학 지식은 아키텍처의 **검증 기준(acceptance criteria)을 정의하는 데 직접 기여**합니다. 이는 모델 출력의 참/거짓을 넘어 "임상·규제적으로 의미 있는가"를 가르는, 복제 불가능한 설계 입력입니다.

## 창업 관점

오늘의 아키텍처는 캡스톤 산출물의 기술적 뼈대이자 투자 설득의 핵심 자료입니다.

**1. 아키텍처 다이어그램 한 장이 "기술 실현 가능성"을 증명한다.** 투자자(Day 94 피치)는 "이 팀이 실제로 만들 수 있는가"를 묻습니다. 위의 5-레이어 도식은 "범용은 사고, 해자(L3)만 만든다"는 **자본 효율적 실행 계획**을 한눈에 보여줍니다. 이는 Day 92에서 설계한 저-번(low-burn) 팀 구성과 Day 91의 빠른 PMF 전략을 기술적으로 뒷받침합니다.

**2. 해자의 위치가 비즈니스 모델을 결정한다.** 해자가 L3(규제 번역)에 있으므로, 비즈니스 모델(Day 86)은 "제약사·바이오텍에 규제 문서 품질을 높이는 SaaS 구독"으로 수렴합니다. 만약 해자를 L2(물성 예측)에 두려 했다면 성숙한 오픈소스·경쟁사와 정면충돌했을 것입니다. **아키텍처 결정이 곧 시장 포지셔닝(Day 84)**입니다.

**3. 바이브코딩으로 MVP를 몇 주 안에 세운다.** L1·L2·L5를 오픈소스·API로 조달하면, 창업자는 바이브코딩(Claude Code, Phase4 W1)으로 L3·L4·L5를 빠르게 조립할 수 있습니다. MVP(Day 91)는 "한 종류의 규제 문서(예: ADMET 요약 섹션) 초안 생성 + 전문가 검토 UI"로 범위를 좁혀, 2~4주 내 데모 가능한 수준을 목표합니다. 완벽한 파이프라인이 아니라 **한 쐐기(wedge)만 뚫는 MVP**가 핵심입니다.

**4. 아키텍처는 기술 부채와 확장성의 사전 계약이다.** 레이어 경계를 명확히 해 두면, 초기엔 단일 서버·관리형 DB로 시작했다가(저비용) 고객이 늘면 L2·L3를 독립 서비스로 분리(Phase4 W2 MLOps·배포)하는 확장 경로를 미리 확보합니다. "지금 빠르게, 나중에 확장 가능하게"를 가르는 것이 레이어 설계의 실질적 보상입니다.

> Week 4 진행: 오늘 우리는 비전(Day 96)을 실현할 5-레이어 아키텍처를 설계하고, 해자를 L3(규제 번역)에 배치하며 나머지는 build-vs-buy 원칙으로 과감히 외부에 맡겼습니다. 약사-창업자의 우위는 검증 기준을 임상·규제적으로 정의하는 능력에 있습니다. 다음 Day 98에서는 이 아키텍처와 시장 분석을 하나의 **사업계획서**로 종합합니다.

## 오늘의 과제

1. **(아키텍처 도식화)** 본문의 5-레이어 구조를 참고해, 나만의(또는 규제 번역 SaaS의) **end-to-end 파이프라인 다이어그램 한 장**을 그리세요(손그림·다이어그램 도구 무관). 각 레이어마다 ① 입력 ② 처리 ③ 출력 ④ 이 레이어에 쓸 Phase 2~4의 구체 기술 1개를 적으세요.

2. **(build vs buy 판정표)** 위 각 레이어에 대해 "만들기/사기" 판정과 그 근거를 표로 작성하세요(레이어 | 판정 | 근거 1문장). 작성 후 **"내가 '만들기'로 정한 레이어가 정말 우리의 해자인가, 아니면 그냥 익숙해서 만들려는 것인가?"**를 자문하고, 해자가 아니라면 '사기'로 바꾸세요. 최종적으로 '만들기'는 1~2개로 제한하세요.

3. **(검증 기준 정의)** 해자 레이어(예: 규제 번역)의 출력이 "충분히 좋다"를 판정할 **임상·규제적 acceptance criteria 3개**를 약학 지식을 활용해 작성하세요(예: "독성 플래그는 hERG·간독성 등 규제적 중대도 순으로 우선순위를 표시한다"). 각 기준이 왜 비전문 개발자가 세우기 어려운지 1문장씩 덧붙이세요.

## 참고 자료

- *Designing Data-Intensive Applications*, Martin Kleppmann (2017) — 레이어화·관심사 분리·확장성의 표준 참고서. 과제 1·2의 레이어 경계 설계 기준으로 활용. (원리서로, 특정 AI 도구와 무관하게 유효)
- *Hidden Technical Debt in Machine Learning Systems*, Sculley et al., NeurIPS 2015 — ML 시스템에서 "모델 코드는 전체의 일부일 뿐, 데이터·서빙·검증 레이어가 부채의 원천"임을 보인 고전. build-vs-buy 판정과 L1·L4 설계의 근거.
- RDKit(화학정보학), HuggingFace(사전학습 모델), FastAPI(서빙) — L2·L5를 "사기"로 조달할 때의 대표 오픈소스. 공식 문서 확인 권장(버전·기능은 시점별 상이).
- Isomorphic Labs, Recursion, Schrödinger의 기술 블로그·IR 자료 — 신약개발 적용 표의 1차 출처. 해자 레이어의 위치는 시점별로 갱신되므로 최신본 확인 필요.
